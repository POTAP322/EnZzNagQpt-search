# Text Classifier Search

Консольное Java-приложение для поиска наиболее подходящих отчётов по текстовому запросу пользователя в свободной форме.

## Сборка

mvn clean package

После сборки в `target/` появится `search-1.0.0.jar` — исполняемый fat jar со всеми зависимостями.

## Запуск

java -jar target/search-1.0.0.jar --data path/to/reports.csv --input-file path/to/queries.txt --output-file path/to/result.json

### Аргументы

| Аргумент | Описание |
|---|---|
| `--data` | Путь к CSV-файлу с отчётами. Разделитель — `\|`. |
| `--input-file` | Путь к текстовому файлу с запросами (по одному на строку). |
| `--output-file` | Путь к выходному JSON. Если файла нет — создаётся, если есть — перезаписывается. |

### Формат CSV
```csv
guid|codeName|description  
f91b806e-806f-4717-be82-555a56f7135e|ndfl2_year|Справка о доходах компании в разрезе года  
80e0d395-5ac0-4ac4-9fb2-6431936d178e|clients1|Список клиентов в разрезе регионов
```
### Формат результата

```json
{
  "initTime": 19,
  "result": [
    {
      "search": "Как получить отчет по суммам налогового вычета?",
      "result": ["1a9f7664-9362-4f16-9a9d-7242c0cca6d3"],
      "time": 5
    }
  ]
}
```

- `initTime` — время в миллисекундах от старта программы до готовности к первому поиску (включая чтение CSV и input-файла).
- `result` — массив результатов по каждому запросу.
    - `search` — исходная строка запроса.
    - `result` — массив GUID подходящих отчётов, отсортированных по релевантности.
    - `time` — время поиска по этому запросу в миллисекундах.

## Архитектура
```text
ru.renue.search
├── App                         — точка входа
├── cli
│   ├── ArgsParser              — разбор аргументов командной строки
│   └── AppConfig               — модель аргументов
├── model
│   ├── Report                  — отчёт (guid, codeName, description)
│   ├── SearchResult            — результат по одному запросу
│   └── SearchResponse          — итоговый JSON
├── loader
│   ├── ReportLoader            — интерфейс загрузки отчётов
│   ├── CsvReportLoader         — реализация для CSV
│   ├── InputLoader             — интерфейс загрузки запросов
│   └── FileInputLoader         — реализация для текстового файла
├── search
│   ├── SearchEngine            — интерфейс поискового движка
│   └── KeywordSearchEngine     — реализация с IDF и стеммингом
├── text
│   ├── Stemmer                — обрезка окончаний
│   └── StopWords              — список стоп-слов
└── io
    └── JsonWriter              — сериализация в JSON
    
```
Принципы SOLID:
- каждый класс отвечает за одну задачу (парсинг, загрузка, поиск, вывод).
- новый движок поиска добавляется без изменения App.
- реализации ReportLoader и InputLoader взаимозаменяемы.
- узкие интерфейсы с одним методом.
- App зависит от интерфейсов, а не от реализаций.

## Алгоритм поиска

Поиск основан на классическом информационном поиске без ML.

### Шаги

1. Нормализация текста: нижний регистр, замена ё → е, удаление пунктуации, разбиение на слова.
2. Стемминг: обрезка окончаний (от длинных к коротким, минимум 4 символа)
   для приведения словоформ к одной основе.
3. Фильтрация стоп-слов из запроса.
4. Подсчёт IDF (Inverse Document Frequency) для каждого слова:
   IDF(word) = log(1 + N / DF(word))
   где N — общее число отчётов, DF(word) — число отчётов, в которых встречается слово.
5. Подсчёт score для каждого отчёта: для каждого слова из запроса, найденного в описании, добавляется IDF(word). Совпадение в codeName даёт удвоенный вес.
6. Сортировка по score по убыванию.
8. Порог отсечения: возвращаются только отчёты со score ≥ 80% от максимального.
9. Ограничение TOP_N = 3 (возвращаем не больше 3 отчетов на 1 запрос).

### Оценка сложности

Обозначения:
- N — количество отчётов,
- W — среднее число слов в описании,
- Q — количество слов в запросе,
- U — количество уникальных слов.

| Этап | Сложность |
|---|---|
| Чтение CSV | O(N * W) |
| Построение IDF | O(N * W) |
| Поиск по одному запросу | O(N * (W + Q)) |
| Сортировка результатов | O(N log N) |
| Итого на один запрос | O(N * (W + Q) + N log N) |

Память: O(N * W + U).

## Принятые решения

1. Сколько GUID возвращать? Не более 5 (TOP_N). Дополнительно применяется порог 60% от максимального score.
2. Как считать релевантность? Классический IDF. Редкие слова весят больше частых.
   Стемминг приводит словоформы к одной основе до подсчёта IDF.
3. Что делать с битыми строками CSV? Пропускаются с предупреждением в stderr.
4. Что делать с пустым запросом? Возвращается пустой массив GUID.
5. Что делать, если ни один отчёт не совпал? Возвращается пустой массив.
6. Поиск по codeName? Да, с удвоенным весом.
7. Регистрозависимость? Поиск регистронезависимый.
8. Перезапись output-файла? Если файла нет — создаётся, если есть — перезаписывается.

## Ограничения

- Нет учёта опечаток.
- IDF пересчитывается на каждый запрос. Для нескольких сотен отчётов это миллисекунды.

## Тесты

mvn test

Покрытие:
- ArgsParserTest — разбор аргументов, обработка ошибок.
- CsvReportLoaderTest — чтение CSV, битые строки, краевые случаи.
- FileInputLoaderTest — чтение запросов, пропуск пустых строк.
- KeywordSearchEngineTest — поиск, сортировка, регистронезависимость.
- JsonWriterTest — сериализация, перезапись, создание директорий.
- StemmerTest — стемминг словоформ.
